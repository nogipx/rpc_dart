`RpcWebSocketServer.stop(drainTimeout:)` stops accepting new CONNECTIONS and
then polls `activeResponders` until it reads zero or the budget expires. It
never tells an already-connected peer to stop opening new streams, so it does
not drain — it waits.

Measured with eight parked server-streams holding the count above zero, so the
poll must spend the whole budget on both transports and ADMISSION is the only
variable left:

```
transport   stop took   before   SERVED after   refused after
websocket    3006 ms      164        1347             3
http2        3016 ms      118           4           514
```

**337x more work admitted after shutdown began.** The http2 server sends GOAWAY
first and its own doc says why: that signal "is what makes a gRPC graceful
shutdown CONVERGE rather than merely expire: without it a call issued after
shutdown began is still accepted and served, extending shutdown by work that
arrived after it started." WebSocket has no GOAWAY and rpc_dart's websocket
server has no substitute.

## The damage is not the waiting, it is what happens at the deadline

When the budget expires the endpoints are closed. A call admitted at 2.9 s into
a 3 s drain is killed at 3.0 s — so the calls MOST likely to be cut mid-flight
are the ones the server accepted after it had already decided to shut down.
That is the failure graceful shutdown exists to prevent, and a rolling deploy
reaches it every time.

## The mechanism already exists in core, one layer down

`responder_pipeline.dart:592`:

```dart
// During drain, reject new streams but allow messages for existing ones.
if (_respIsDraining && _respStreams[message.streamId] == null) {
  ... RpcStatus.unavailable, 'Server is shutting down' ...
```

That flag alone is the rpc-level GOAWAY: new streams get UNAVAILABLE (retryable,
which is what a draining server should say), existing ones run to completion.
Neither server sets it. `RpcHttp2Server` does not need to, because GOAWAY covers
it at the transport; `RpcWebSocketServer` has nothing else and does not use it.

## Why it is filed rather than fixed

The only public way to set that flag is `RpcEndpointBase.drain()`, which also
**cancels every active context** with reason `server draining`. That is the
opposite of what `stop(drainTimeout:)` promises — its whole point is to let
in-flight calls finish — so calling it would trade admitting too much for
killing what is already running.

The fix is to split the two halves, which is a core API decision:

```
option                                cost
a `markDraining()` that sets only     new public surface on RpcEndpointBase,
  the flag                            and a second way to say "draining"
a parameter on drain()                changes a published signature
the websocket server reaching in      not available; the field is private
```

Round 403 measured it and stopped there rather than adding core API on its own
authority.

## Owner decision

**Answered: yes, split them.** `RpcEndpointBase` gains a `markDraining()` that
sets only the reject-new-streams flag; `drain()` keeps both halves for the
callers that want them. The websocket server's `_drain` calls it on every
endpoint before polling, which is the GOAWAY it has no protocol equivalent for.

The question as put was whether to expose "reject new streams" separately from
"cancel the active ones". Every graceful drain wants the first without the
second, and today only `rpc_app.dart` uses `drain()` at all — the two servers
each hand-rolled their own polling loop instead.
