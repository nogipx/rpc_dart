The same question — a non-200 HTTP response, what gRPC status is that — is
answered by two tables that disagree on six rows.

```
  HTTP   rpc_dart_http                  rpc_dart_http2
         _httpStatusToGrpcCode          grpcStatusFromHttpStatus
         (caller transport:59-98)       (rpc_http2_common.dart:433-440)

  400    invalidArgument                internal
  429    resourceExhausted              unavailable
  500    internal                       unknown
  504    deadlineExceeded               unavailable
  409,410,412,413,415,499,501  mapped   unknown
  default >=500 internal, >=400 invalidArgument     unknown
```

## The row that changes behaviour rather than wording

**504.** `RpcRetryInterceptor` retries `unavailable` and `resourceExhausted` and
nothing else — the http2 table's own doc comment says so, in the course of
explaining why collapsing statuses to `internal` was wrong. A gateway timeout
from a proxy is therefore **retried over HTTP/2 and final over HTTP/1.1**, for
the same deployment, the same proxy and the same application code. Swapping the
transport silently swaps the retry policy.

429 differs in name only — both sides land on a status the interceptor retries.
400, 500 and the defaults change the status the application sees but not whether
it is retried.

## Which one is right is not obvious, and that is the point

The http2 table is the narrower and the better-argued: its comment states the
rule that anything not in the table is `unknown` rather than `internal`, because
"the peer said something gRPC has no meaning for". By that rule the HTTP/1.1
table's `>= 400 -> invalidArgument` default is wrong.

But the HTTP/1.1 table is the more complete, and several of its extra rows are
right: 413 to `resourceExhausted` and 401/403 are the mappings gRPC's own
gateway documents. And `504 -> deadlineExceeded` is arguably the more honest
status, which would make the http2 row the one to change — at the cost of making
a proxy timeout non-retryable there.

**So this is an owner decision before it is a refactor.** One table, in core
beside `wireStatusFor`, with the rows settled once.

## Related, same seam, not verified here

The sweep that produced this also reported, and these were NOT re-checked at
`ff930001` — see B-70:

- HTTP/1.1 treats only `grpc-status` and `grpc-message` as trailers, while
  `RpcMetadata.forTrailer` also writes `grpc-status-details-bin`, so
  `RpcStatusException.details` would always be empty over HTTP/1.1. If true this
  compounds B-64 #1: two independent paths that drop the same field.
- The CORS expose-list mirrors that same omission.
- `content-type` is required by HTTP/1.1, accepted when absent by the pipeline,
  and unchecked in the http2 responder.

## Owner decision

**"Backward compatibility does not matter, make it perfect."** That settles the
rows on merit rather than on who breaks least.

## Closed — round 417

One table, `grpcStatusFromHttpStatus` in `protocol.dart` beside `wireStatusFor`,
called by both transports.

**The base is grpc-go's `HTTPStatusConvTab`** — the http2 table was already
exactly that, and it is what a gRPC peer and every gateway assume. 504 is
`unavailable` on both transports now, so the retry policy no longer depends on
which transport is plugged in.

**Two rows are kept beyond it, and an EXISTING test is why.** The plan was to
adopt grpc-go's table wholesale; `oversized_request_is_resource_exhausted_test`
failed and its header names its direction — rpc_dart's own responders answer
**413** for a body over `maxMessageLengthBytes`, and RESOURCE_EXHAUSTED is what
tells the caller it hit a SIZE it can reduce rather than sent malformed
arguments. The argument for dropping it (RESOURCE_EXHAUSTED is retryable, and
retrying an oversized body is futile) is the weaker one: the remedy is the
caller sending less. **499** is kept on the same test — nginx emits it and
CANCELLED is its exact inverse in gRPC's gateway mapping.

Gone: 409, 410, 412, 415, 501 and the `>=400 -> invalidArgument` default. No
rpc_dart responder emits those, and the `unknown` rule covers them.

**The three "related, same seam" items are still unverified** and stay B-70's.
