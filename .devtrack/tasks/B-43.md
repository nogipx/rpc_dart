## The code fact

```js
function _rpcWasmSendBytes(bytes) {
  fetch('rpc-wasm:///send', {method: 'POST', body: bytes});
}
```

Unawaited, so N fetches are in flight at once. The order the Swift scheme
handler sees them in is WebKit's dispatch order — conventional, not
contractual. Android has no equivalent exposure: the guest pushes into a JS
array the driver drains in order, FIFO by construction.

Ordering matters more here than "messages arrived shuffled" suggests.
`RpcChannelTransport` reassembles a byte STREAM, so two frames swapped on the
wire are corruption: the second frame's header is read from the middle of the
first frame's payload.

## What was measured

```
platform  frames  in order  elapsed
android   10000   yes       2161-2808ms
ios       10000   yes       5006-14695ms
```

iOS 18.6 simulator, 10000 frames from one server-stream, compared against the
generated sequence so a swap, a duplicate or a gap all fail. **The convention
holds.** This is the first measurement in the repository that it does, rather
than an assumption.

## Why the fix is not applied

The proposed fix chains the fetches:

```js
var _sendChain = Promise.resolve();
function _rpcWasmSendBytes(bytes) {
  _sendChain = _sendChain
      .then(function() {
        return fetch('rpc-wasm:///send', {method: 'POST', body: bytes});
      })
      .catch(function() {});
}
```

That is correct and it makes the guarantee contractual. It also **serialises
every send**: no two POSTs in flight, so each frame pays a full scheme-handler
round trip before the next starts. The 5.0 s figure above is with pipelining;
without it, 10k frames pay 10k sequential round trips.

The config's standing owner requirements include: *"Ask before trading speed for
anything else. Mentioning the cost in the report is NOT asking: a round once
removed a fast path for correctness and the owner objected."* This is exactly
that shape, so the round asked instead of shipping.

## Owner decision

**Taken (after round 379): option 1 — leave it.**

The chain buys a contractual guarantee by removing exactly the pipelining the
measured figures rest on, and the convention it would replace was checked rather
than assumed: 10000 frames in order on both platforms. `guest_to_host_order_test`
is in the suite and fires if a future WebKit changes the dispatch order, so the
assumption is watched rather than trusted.

What this does NOT say: that the ordering is contractual. It is not, and the
record above explains why that matters here specifically — the channel
reassembles a byte STREAM, so two swapped frames are corruption. Re-open if the
witness ever fires, or if iOS traffic grows enough that "10000 frames held" stops
being a comfortable margin.

Nothing to carry out, so this closes rather than waiting for a round.

The three options, for the record:

1. **Leave it.** The convention holds over 10k frames today, and the
   `guest_to_host_order_test` in the suite is a regression witness that fires if
   a future WebKit changes it — on a simulator run, not in production.
2. **Chain unconditionally.** Contractual ordering, at the cost of pipelining.
   Worth measuring the new 10k figure before committing to it; if the cost is
   small the trade is cheap.
3. **Chain with a window** — allow K sends in flight and order the handler side
   by a sequence number instead. Keeps most of the pipelining and makes ordering
   explicit, at the price of a sequence field in the protocol and reordering
   logic in Swift.

Round 365 has no recommendation, because the choice turns on how much the
throughput is worth to you, which the loop cannot measure.
