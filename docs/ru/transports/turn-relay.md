# TURN релейный транспорт

`RpcTurnRelayServer` добавляет в `rpc_dart_transports` реализацию UDP-релея в
стиле RFC 5766. Сервер принимает TURN-запросы, создаёт выделения (allocations),
пересылает исходящие датаграммы к пирам и доставляет ответы обратно клиенту.
Всё написано на Dart и использует те же средства логирования и диагностики, что
и другие транспорты RPC Dart.

## Что реализовано

- **Хелперы для TURN/STUN кадров** — `TurnMessage`, `TurnAttribute` и функции
  кодирования покрывают XOR-адреса, полезную нагрузку, ChannelData и атрибуты
  времени жизни из RFC 5389/5766.
- **Жизненный цикл выделений** — `TurnAllocation` управляет UDP-сокетом релея,
  таймером истечения, разрешениями для пиров и привязками каналов.
- **Обработчики методов TURN** — сервер отвечает на `Allocate`, `Refresh`,
  `CreatePermission`, `ChannelBind` и `Send`, а входящий трафик от пиров
  отправляет клиенту через `Data` индикации или ChannelData кадры.
- **Отдельные UDP-сокеты для пиров** — каждое активное выделение открывает
  собственный порт на relay-адресе, чтобы трафик ходил напрямую между пиром и
  релеем, не мешая управляющему TURN-порту.

## Когда использовать

TURN-релейный сервер пригодится, если:

- нужен **инструмент обхода NAT** для WebRTC или других двунаправленных
  UDP-протоколов;
- вы уже используете **rpc_dart** в управляющем слое и хотите переиспользовать
  те же логеры, хуки жизненного цикла и деплой вместо отдельного coturn;
- нужно **реагировать на события TURN** из бизнес-логики: выдавать квоты,
  инспектировать активных пиров или запускать RPC по появлению новых выделений.

## Запуск сервера

```dart
import 'package:rpc_dart/rpc_dart.dart';
import 'package:rpc_dart_transports/rpc_dart_transports.dart';
import 'package:universal_io/io.dart';

Future<void> main() async {
  final relay = RpcTurnRelayServer(
    bindAddress: InternetAddress.anyIPv4,
    port: 3478,
    logger: RpcLogger('turn'),
  );

  await relay.start();
  print('TURN relay: ${relay.bindAddress.address}:${relay.listenPort}');

  // ...приложение продолжает работать...

  await relay.stop();
}
```

По умолчанию в `XOR-RELAYED-ADDRESS` попадает bind-адрес. Передайте
`relayAddress`, если релей стоит за NAT или нужно рекламировать другой IP.

## Управление выделениями и пирами

`RpcTurnRelayServer` хранит коллекцию активных `TurnAllocation`, к которым можно
обращаться из приложения. Внутри доступны:

- `clientAddress` / `clientPort` — сокет TURN-клиента;
- `relayPort` — порт, на который должны отправлять датаграммы пиры;
- разрешения и каналы — можно проверять, каким адресам разрешён доступ;
- колбэк `onPeerData` — вызывается при получении пакета от пира, после чего
  сервер отправляет клиенту `Data` индикацию.

Выделения истекают автоматически через `allocationLifetime` (по умолчанию 10
минут). Запросы `Refresh` продлевают время жизни, а просроченные разрешения и
каналы удаляются по мере проверки.

## Сценарий взаимодействия клиента

1. **Allocate** — отправьте запрос с `REQUESTED-TRANSPORT = UDP`. В успешном
   ответе придёт `XOR-RELAYED-ADDRESS` с адресом/портом релея и собственный
   `XOR-MAPPED-ADDRESS` клиента.
2. **CreatePermission** — выдайте разрешения для нужных пиров через
   `XOR-PEER-ADDRESS`.
3. **Отправка данных** —
   - используйте индикации `Send` с `XOR-PEER-ADDRESS` и `DATA`, или
   - привяжите канал `ChannelBind` и шлите компактные ChannelData кадры.
4. **Получение ответов** — входящие пакеты превращаются в `Data` индикации (или
   ChannelData) и пересылаются клиенту.
5. **Refresh / завершение** — `Refresh` продлевает выделение, а нулевая
   длительность немедленно его завершает.

Интеграционный тест `rpc_turn_relay_server_test.dart` показывает полный цикл,
включая обратный трафик от пира.

## Вспомогательные API для TURN сообщений

`TurnMessage` облегчает работу с бинарным форматом TURN/STUN:

- `TurnMessage.encode()` / `TurnMessage.decode(...)` преобразуют объекты Dart в
  UDP-пакеты и обратно;
- `encodeXorAddress`, `decodeXorAddress`, `encodeLifetime`, `encodeData` и
  функции для ChannelData избавляют от ручного построения буферов.

С помощью этих утилит можно быстро писать тесты, интегрироваться с готовыми
клиентами или строить собственные инструменты.

## Ограничения и планы

- Поддерживаются только **UDP-выделения**; TCP, DTLS и TURN-over-TLS не
  реализованы.
- **Аутентификация отсутствует** — нет ни краткосрочных, ни долгосрочных
  креденшелов. Ограничьте доступ сетевыми правилами или добавьте свою
  авторизацию до публикации сервиса.
- Пока нет квот на пропускную способность и механизма ALTERNATE-SERVER.

Тем не менее, сервер уже подходит для приватных окружений, тестов и прототипов,
а также как база для дальнейшего расширения функциональности.
