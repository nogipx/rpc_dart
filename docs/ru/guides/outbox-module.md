# Подключаемый outbox-модуль

Ниже — вариант подключаемого outbox-модуля для RPC Dart с акцентом на
переиспользуемость и единообразие контрактов.

## Базовые принципы
- Используйте контракты RPC Dart для описания методов outbox и маршрутов
  транспорта: Caller/Responder остаются единым способом общения между
  приложениями, воркерами и инфраструктурой.
- Включайте health/reconnect для автоматического восстановления транспорта и
  наблюдаемости за очередью.
- Для in-process сценариев (воркер в изоляте рядом с приложением) применяйте
  zero-copy режим InMemory/Isolate-транспорта, чтобы не сериализовать события
  лишний раз.

## Контракт
- Методы: `enqueue(events)`, `claim(batchSize, shard)`, `ack(ids)`, `nack(ids, reason)`,
  `peek`, `metrics`.
- Модели: `OutboxEvent`, `OutboxClaimRequest/Response`, `OutboxMetrics`,
  idempotency key и метаданные ретраев.

## Роли
- **Responder** хранит события в хранилище, выполняет повторные попытки,
  дедупликацию и обеспечивает idempotency. Health-ответ отражает состояние
  хранилища и транспорта.
- **Caller** — обёртка для приложений и воркеров: `callUnary` для CRUD-операций,
  `stream` (опционально) для live-feed.
- **Transport plug-in** — WebSocket/HTTP2/Isolate, маршрутизация через
  `RpcTransportRouter` по имени сервиса или заголовкам.

## Хранилище: rpc_dart_data
- Для хранения событий используйте `rpc_dart_data` как единый слой данных:
  он обеспечивает согласованные интерфейсы и транзакционность для SQL/NoSQL
  бэкендов.
- Реализуйте адаптеры `SqlOutboxStore`, `FileOutboxStore`, `InMemoryOutboxStore`
  на базе абстракций `rpc_dart_data`, чтобы переиспользовать модели и
  транзакции без дублирования кода доступа к данным.

## Интеграция с event-driven потоком
1. Producer сервис пишет бизнес-данные в БД и параллельно кладёт запись в
   outbox (в одной транзакции, если поддерживается хранилищем из
   `rpc_dart_data`).
2. Фоновый воркер через Caller вызывает `claim` для батча задач, публикует их в
   брокер/шину и подтверждает `ack`.
3. При ошибках воркер вызывает `nack`; поля retry/backoff обрабатывает
   Responder, health сигнализирует о состоянии очереди.
4. Для мультисервисного использования публикуйте общий пакет
   `outbox_client` (Caller + модели) и `outbox_server` (Responder + адаптер к
   хранилищу), чтобы сервисы просто подключали зависимость и регистрировали
   сервис.

## Расширения
- Шардирование/partition key в `claim` для горизонтального масштабирования
  воркеров.
- Dead-letter queue и экспоненциальный backoff в Responder.
- Метрики (возраст старейшего события, длина очереди, скорость обработки) с
  экспортом через health API.
