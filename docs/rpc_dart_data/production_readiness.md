# rpc_dart_data: план превращения в готовый удалённый сервис "поднял и пользуюсь"

Цель этого документа — описать минимальный набор улучшений, который позволит
воспринимать `rpc_dart_data` как готовую удалённую базу данных: запустил
сервер/контейнер, подключил клиентов и сразу работаешь с коллекциями без
дополнительной инфраструктуры. Мы фокусируемся на односерверном варианте,
который достаточно прост, чтобы использовать его в собственных проектах как
универсальное хранилище.

## Каким должен быть опыт использования

* **Один бинарь или контейнер.** Команда `dart run bin/serve.dart` или запуск
  готового образа поднимает сервис со встроенным хранилищем и журналом.
* **Автоинициализация.** При первом старте создаётся файл базы, необходимые
  таблицы и каталог для журнала без ручных миграций.
* **Прозрачные коллекции.** Создавать/удалять коллекции можно через RPC без
  дополнительных SQL-скриптов.
* **Готовые бэкапы.** Есть понятный способ сделать снапшот и восстановиться
  после сбоя.
* **Понятные настройки.** Всё конфигурируется через YAML/ENV (путь до файла,
  размер журнала, ключи secure-wrap).

## Базовый объём функциональности (single-node MVP)

| Возможность | Статус | Как реализовано |
|-------------|--------|-----------------|
| **Персистентное хранилище по умолчанию** | ✅ Готово | CLI `serve` всегда поднимает `DriftDataStorageAdapter.file(...)`, автоматически создаёт каталог и, при необходимости, применяет SQLCipher. |
| **Минимальный журнал изменений** | ✅ Готово | Добавлен `DataChangeJournal` с реализацией на SQLite (`DriftDataChangeJournal`), `watch()` и `sync()` читают историю из таблицы `change_journal`. |
| **Индексы и фильтрация на стороне хранилища** | ✅ Готово | `DriftDataStorageAdapter` объявляет индексы на `version/created_at/updated_at` и умеет выполнять `list()` с фильтрами, пагинацией и сортировкой в SQL. |
| **Атомарные записи** | ✅ Готово | `bulkUpsert` и `importDatabase` агрегируют записи и передают их в `writeRecords`, которое применяет транзакцию на уровне SQLite. |
| **Встроенные бэкапы** | 🛠️ В процессе | Экспорт/импорт доступны через RPC, но удобный CLI сценарий и автоматизация бэкапов/restore ещё в работе. |

Эти пять пунктов закрывают основные проблемы текущей реализации и делают
`rpc_dart_data` самодостаточным сервисом для большинства pet-проектов и
внутренних инструментов.

## Что откладываем на потом

Чтобы не перегружать сервис, явно помечаем функции, которые не входят в
"базу данных на вечер":

* Шардирование, распределённый консенсус, автоматический failover.
* Сложная политика безопасности (RBAC/ABAC) — достаточно токена и хука на
  уровне репозитория.
* Расширенные аналитические запросы и полнотекстовый поиск (оставляем как
  опциональные плагины к моменту, когда они действительно понадобятся).

## Пошаговый план реализации

1. **Завершить эксплуатационные сценарии.**
   * Добавить команды `backup`/`restore` в CLI и рецепты для cron.
   * Документировать рекомендуемые лимиты журнала и периодическую очистку.
2. **Улучшить наблюдаемость.**
   * Простейшие метрики (`collections_total`, размер журнала, последнее время бэкапа`).
   * Интеграция с системными health-check-ами контейнера.
3. **Расширить поиск при необходимости.**
   * Подключить FTS5 для полнотекстового поиска.
   * Добавить декларативные индексы для произвольных полей коллекций.

## Минимальная эксплуатация

* **Monitoring-lite:** достаточно логов о старте/остановке, количестве
  коллекций и объёме журнала. Метрики Prometheus можно оставить на будущее.
* **Резервное копирование:** cron-задача, которая вызывает `exportDatabase`
  и складывает JSON в S3/локальный диск. Важно протестировать `import` на
  отдельном стенде.
* **Аутентификация:** используйте `--auth-token`/`--auth-token-env`/`--auth-token-file`
  для выдачи backend-ключей и держите сервис за ingress-прокси, который обеспечит TLS.
* **Обновления:** при изменении схемы/индексов `serve.dart` применяет миграции
  автоматически через Drift. Если миграция не прошла, процесс падает и не
  стартует, что проще отлаживать.

## Дорожная карта на ближайшие релизы

| Релиз | Основные пункты |
|-------|-----------------|
| **0.9** | `singleNode` профиль, `SqliteChangeJournal`, транзакции в Drift адаптере |
| **0.10** | Индексы + декларации, делегирование фильтров в адаптер |
| **0.11** | CLI для backup/restore, документация и примеры деплоя (Docker/Just) |

После выполнения этих задач `rpc_dart_data` станет лёгким в запуске удалённым
хранилищем: вы получаете готовый RPC слой, управляемые коллекции и устойчивые
подписки без необходимости поднимать отдельную СУБД или писать обвязку.
