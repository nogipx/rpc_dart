# B-01 — Метаданные ответа отбрасываются целиком

Статус:   ждёт владельца — нужна его решение о форме API
Раунд:    141 (не перепроверено)
Проба:    `rpc_dart/.dart_tool/probe/response_metadata_visibility.dart`

rpc_dart выбрасывает ВСЕ метаданные ответа между транспортом и приложением.
Измерено с сырого пира через канальную пару — собственный респондер rpc_dart тоже
не умеет ОТПРАВЛЯТЬ произвольные метаданные ответа, поэтому пара
rpc_dart-с-обеих-сторон не отличила бы «отброшено» от «не отправлено»:

    пир отправил, заголовки : {x-ratelimit-remaining: 42, x-server-build: abc123}
    пир отправил, трейлеры  : {x-rows-scanned: 1000}
    приложение получает     : RpcString "pong"   <- и больше ничего
    API для этого           : на RpcCallerEndpoint нет

Данные уже на месте: приходят обычным кадром метаданных, читаются в
`rpc/streams/unary/caller.dart` и в трёх потоковых вызывающих, где достают только
`grpc-status`, `grpc-message`, `grpc-encoding`, а остальное роняют.

Против настоящего gRPC-сервера это дыра совместимости, а не отсутствие удобства:
бюджеты rate limit, курсоры пагинации, `retry-after`, auth-челленджи.

## Почему не сделано в раунде

Это ДВЕ фичи, и половина не помогает почти никому:

1. вызывающий может ЧИТАТЬ метаданные ответа — ценно только против чужих серверов;
2. обработчик респондера может их СТАВИТЬ — без этого пользователи
   rpc_dart-с-обеих-сторон не получают ничего.

## Рекомендованная форма, если владелец захочет

Аддитивно, без ломки, одинаково для всех четырёх форм вызова: коллектор
параметром, а не колбэк — никаких сюрпризов с порядком, один параметр, читается
после вызова.

```dart
final meta = RpcResponseMetadata();
final r = await caller.unaryRequest(..., responseMetadata: meta);
meta.headers['x-ratelimit-remaining'];
meta.trailers['x-rows-scanned'];
```

Серверная половина — зеркало на `RpcContext`: обработчик пишет, конвейер
респондера сливает в начальные заголовки и в трейлер.
