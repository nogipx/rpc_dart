## Awaiting an owner decision

Re-sorted in the audit after round 287, which found this section holding one
CLOSED lead and a paragraph of orphaned prose while the two leads that actually
await a decision sat under "Open". They are MEASURED; what is missing is a
choice about what the library promises, not a number.

**Round 350 is the warning against over-using this section.** B-28 sat here for
68 rounds framed as "either pace metadata or bound the buffer, ask the owner" —
and one of the two was never available: HTTP/2 exempts HEADERS from flow control
for a deadlock reason the spec states. What looked like a trade about library
behaviour was a question the protocol had already answered. Before parking a lead
here, check that both branches actually exist.

- **[B-43](B-43-ios-send-order-is-a-convention.md)** open, owner decision (round 365) — iOS `_rpcWasmSendBytes` does an UNAWAITED `fetch` per frame, so N are in flight and the order the Swift scheme handler sees them is WebKit's dispatch order — conventional, not contractual. Ordering is not cosmetic here: `RpcChannelTransport` reassembles a byte STREAM, so two swapped frames are corruption, not a reordered pair. **Measured: the convention holds** — 10000 frames in order on both platforms, iOS in 5.0-14.7 s, the first time this has been checked rather than assumed. The proposed promise chain makes the guarantee contractual and **serialises every send**, removing the pipelining those figures rest on — a speed trade, and the config's standing requirement is to ASK before making one. Three options in the lead (leave it with the regression witness now in the suite; chain unconditionally; chain with a window plus a sequence number), no recommendation, because the choice turns on what the throughput is worth
- **[B-42](B-42-ios-strip-failfast-unwitnessed.md)** **closed (round 365)** — round 363's module-syntax fail-fast shipped in BOTH plugins with only the Android half witnessed, on the argument that it adds a check to an already-failing path (so a false negative leaves today's behaviour) and that the dangerous direction — the false POSITIVE of refusing working glue — lives in the line-anchoring rule, which is identical in both languages and was measured on Android (`+21 ~2` → `+3 ~2 -13` when made naive). **A simulator came up and settled it: all five witnesses pass on iOS 18.6 unchanged (`+26`).** The check fires correctly on the other engine and the control still boots. The argument turned out to be right, which is recorded precisely because it might not have been. Still unmeasured, and not worth a device run of its own: nobody ablated the check ON iOS to confirm the 30 s watchdog is what it replaces there — a question about the old behaviour, not about the fix
- **[B-41](B-41-android-base64-on-the-main-thread.md)** open, reason "bench" (round 362) — **the code fact is certain and the impact is not.** `CoroutineScope(Dispatchers.Main)` puts `Base64.encodeToString` per sub-64-KiB frame, `Base64.decode` over batches of up to 4 MiB per drain, and an `allocateDirect`+`put` per frame on the thread that dispatches every platform channel in the app. The fix was written, type-checks (`PASS swift / PASS kotlin`) and keeps the device suite green — and **five emulator runs could not tell it from its own ablation**: with Base64 put back on Main the main thread read 38 ms busy against 39 ms idle, no worse than the fixed state and better than the fixed state's own 70 ms. Idle worst ranges 12-39 ms, the size of the effect. **The negative is informative**: the occupancy is real (busy clearly worse than control in 3 of 5 runs) but does not come from Base64 — the remaining candidates cannot be moved, `evaluateJavaScriptAsync` marshalling 4 MiB across Binder and `messenger.send`, which must be on Main by contract. Also: the item's criterion ("no frames >16 ms") is unmeetable on this emulator, where the IDLE control alone exceeds it. Needs a physical device, or an in-plugin timer instrumenting both arms identically; the fix is written out in the lead
- **[B-40](B-40-method-path-from-key-drops-dots.md)** open, below the bar (round 360) — `_methodPathFromKey` splits a method key on EVERY dot, so `myapp.v1.UserService.Get` yields four parts and returns `/UnknownService/UnknownMethod`, while its sibling `_parseMethodPath` validates against `[A-Za-z0-9_.-]+` and admits those names DELIBERATELY — which is also what gRPC uses for fully-qualified protobuf services. Real drift, in one file. **The ordinary path is clean, measured**: dotted names round-trip, because `methodPath` rides on the frame and the formatter is consulted only when both retained messages are null while `methodKey` is set; round 360 did not build a witness that reaches it. The damage there is a wrong diagnostic STRING nothing routes on, so it is below the config's bar. The four-line fix (split on the LAST dot — a method name cannot contain one) is written out in the lead, to be applied by any round that touches the method for another reason
- **[B-39](B-39-websocket-send-throws-into-the-root-zone.md)** open, owner decision (round 358) — `RpcWebSocketChannel.send` calls `_ws.sink.add` unguarded, and in the one turn between our OWN raw socket closing and `onDone` arriving it throws **into the ROOT zone**, which ends the isolate. **A peer close is NOT this defect** — the sink keeps accepting until it learns, measured across four arms — so the item's framing was wrong about both reachability and severity. **Both obvious fixes were applied and measured not to work**: `try { sink.add } catch (_) {}` changes nothing, and neither does `runZonedGuarded` at the call site, because `WebSocketSink.add` queues into a StreamController and the real `sendBytes` runs a microtask later in the zone that CONTROLLER was built in. What does work, measured: constructing the `WebSocketChannel` inside `runZonedGuarded` — the same arm returns normally and the construction zone receives the error. That makes it fixable at the library's own entry points (`connect()`, the server's accept path) and unfixable for a user-supplied socket. The decision is whether to zone-guard construction, which reroutes EVERY async error from that channel, not only send failures — **the identical decision B-35 is waiting on, one dependency over, and worth deciding together**. Guarded by `send_after_raw_socket_close_test.dart`, whose three GUARDs pin what is not broken
- **[B-38](B-38-ios-recv-loop-dies-silently.md)** open, reason "bench" (round 357) — **the finding needs no device and is conclusive; the fix does and could not be run.** iOS drives host-to-guest with one long-poll `fetch('rpc-wasm:///recv')` whose `.catch` sets `_recvRunning = false` and returns — nothing restarts it, nothing reports it, so the direction is dead and silent while `recvQueue` grows and every in-flight call waits out an OPTIONAL deadline. **Android's driver loop already fixed exactly this**, and its comment describes the iOS behaviour: *"the isolate stayed in runtimes, nothing further was evaluated, and Dart was never told -- so every in-flight call hung"*; iOS does not even log. Reachable without the host stopping: `webView(_:stop:)` when WebKit cancels a scheme task, or a second `/recv` failing the first with "superseded by new recv". The fix was written and `analyze:native` returned `PASS swift / PASS kotlin` — **and was REVERTED**, because round 348 established what a gate never shown to fail is worth, and a native change nobody ran is what this project's config says must not ship. The lead carries the four-step patch, the witness design, and the two traps: back off through `_nativeSetTimeout` (the next tag declares a hoisted `setTimeout` POLYFILL that queues into the guest's own timer table) and report death by `postMessage`, not by a fetch of the scheme that just stopped answering. **Needs a booted simulator, not a decision** — five launch attempts and waits up to 240 s never registered a device, though one booted earlier in the same session
- **[B-37](B-37-endpoints-getter-excludes-peers.md)** open, owner decision (round 354) — `RpcWebSocketServer.endpoints` is `whereType<RpcResponderEndpoint>()` over a list that deliberately holds BOTH kinds, so a server built with `onPeerEndpointCreated` reports zero endpoints however many connections it is serving. `stop()` is unaffected (it iterates the field, not the getter); what is affected is anyone asking the server what it is serving. **The type is the obstacle, not the logic**: the return type is fixed by `IRpcServer.endpoints`, `List<RpcResponderEndpoint>`, implemented by all three servers, and `RpcPeerEndpoint`/`RpcResponderEndpoint` are sibling subclasses with no narrower common type. So the choice is between widening a published interface (breaking, across three packages), adding a second getter (additive, leaves a getter that lies for one mode), and documenting the narrowing. No recommendation: the three differ in what they promise callers
- **[B-36](B-36-the-abandon-timer-fabricates-a-success.md)** open, owner decision (round 351) — the circuit breaker's probe abandon timer calls `resolve(success: true)`, so a probe that produced **no item, no error and no done event** is recorded as a recovery: `_onSuccess` zeroes the failure count and CLOSES the breaker, reopening full traffic to a service nothing observed. Not round 351's wedge class — this ending does release the gate, it just answers wrongly — and `audit_circuit_breaker_abandoned_probe_test.dart:155` pins `closed` there with a reason that names the RELEASE, so changing it means deciding which of the two the test was protecting. One line now that 351 added `_releaseProbe()`; the recommendation is to leave the breaker half-open, which is what every other inconclusive ending in this class already does
- **[B-35](B-35-finish-throws-into-the-zone.md)** open, MEASURED (round 347) — `package:http2`'s `finish()` throws `StateError: Cannot add event after closing` into the zone **after its own future has completed**, so it is not a rejection and no handler at the call site sees it: `unawaited(terminate())` after finish, `terminate().catchError(...)` after finish, and **`finish()` with nothing after it at all** all produce it, which is what identifies the source. Three neighbouring states do not (terminate live, terminate twice, terminate after socket destroy). A lead rather than an incident because **the transport's own `close()` does not reach it** — measured over connect / call / close / close-again inside `runZonedGuarded`, nothing escapes, since close() RSTs every stream before calling finish() and rounds 346-347 could not make it time out even with the budget forced to 1 ms and to zero. Any fix is a design decision: only a zone contains it, and zone-guarding changes where genuine transport errors surface. **Do NOT fix it at the call site** — two attempts measured, both ineffective. Guarded by `finish_throws_into_the_zone_test.dart` so the lead closes itself if the dependency changes
